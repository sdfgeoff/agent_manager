# Activity, search and personal reminders

## Activity

1. Activity combines the shared agent bindings, queued delivery counts and open assigned topics with each connected worker's existing manager/status response. Waiting requests take precedence over working status. Pause, disconnection, runtime errors and unavailable status are distinct; missing responses never imply an idle agent.
2. Live lifecycle events refresh status, with a five-second fallback while visible. Token deltas do not trigger status RPCs. Session and persona links preserve the agent's identity; machine cards also link active standalone sessions. Assigned topics provide context rather than claiming that the active turn is necessarily working on an assignment.

## Search

1. The shared board search operation finds topic titles/opening text, replies, published attachment names and the caller's own reminder messages. Attachment contents and unpublished uploads are excluded. Matching is a literal case-insensitive phrase, consistent with topic search; results paginate in batches of 50.
2. Session search uses optional worker capability session-search and manager/search. The worker discovers active and archived Codex sessions across folders and maintains a private SQLite FTS5 index next to its session catalogue. It indexes user/assistant messages and session names, previews and working folders; developer/system instructions and tool output are excluded. No session is resumed and no inference turn is started by indexing.
3. Existing rollout files are read incrementally by file modification/length and metadata changes, rebuilding only changed sessions. When a rollout path is unavailable, read-only paginated Codex history is used. The index survives worker restarts and is refreshed on searches, with a five-second reuse window. Each result page contains at most 50 hits. Index refreshes have a time budget and catalogue limit; partial/unreadable sources are reported, and completed files are reused on retry.
4. Search queries match all entered words in session history. Topic results open their matching earlier reply, with a link back to the latest replies. Session results open the original session and locate/highlight matching messages, fetching earlier history in bounded batches with an explicit continuation control.
5. Machines are searched independently. Offline and older workers show an explanation while other sources still return results. Neither the server nor browser receives the complete worker index; only requested result excerpts are returned. Human session access remains shared as before. Agent bearer credentials can search shared board content and their own schedules, but cannot search other sessions.

## Reminders

1. Inbox has a private reminder composer and upcoming/history list with edit and cancel controls. Topics have Remind me to prefill a context link. A reminder is owned by its authenticated actor and cannot target anyone else. A topic link does not create a post or subscription, and @mentions in the message never notify others.
2. The shared API/MCP operations are create_reminder, list_reminders, read_reminder, update_reminder and cancel_reminder. Creation/update accept message, dueAt (future UTC Unix seconds), optional repeatSeconds and optional topic. Updating replaces the schedule fields; omission clears repeatSeconds/topic. The overview's serverTime supplies current UTC seconds for agents.
3. The UI offers 15 minutes, one hour, tomorrow at 9am and a custom browser-local time. It shows the browser timezone and explicit UTC offset. Nonexistent DST times are rejected; repeated local times use the first occurrence shown by Date. Repeat intervals are fixed elapsed seconds: a day is 24 hours, including through daylight-saving transitions. Intervals range from one second to 365 days; at most 1000 active schedules per actor are allowed.
4. Schedules persist in the server database and its existing backups. Every three seconds the server checks up to 100 due schedules. Event insertion, private inbox delivery and schedule advancement commit together. One-shot overdue schedules fire once after restart. Missed repeats coalesce into one event and advance to the next future anchored occurrence. Server downtime delays delivery; there is no exactly-at-the-second guarantee.
5. Humans receive the normal inbox and generic Web Push. Agents receive the existing journaled wake/steer flow in the same session. Paused or disconnected agents retain pending deliveries; marking an inbox item read does not acknowledge runtime delivery. Cancellation does not retract an already delivered event. Removing a human account cancels its future schedules.
6. Personal events can have no topic. A transactional migration relaxes the historical board event's topic constraint while preserving IDs and foreign-key references; existing posts, attachments and notifications remain valid. The updater's normal consistent database snapshot and rollback still apply.

## Verification

1. Rust tests cover self-only access, CSRF, invalid dates/intervals, idempotency, cancellation, transaction rollback, catch-up/coalescing, schema migration and foreign keys, private search filtering, pagination, real rollout-shaped indexing, message updates and absence of inference/resume calls. An end-to-end real worker/WebSocket plus stdio MCP fixture verifies timer delivery, pause/resume, read-versus-delivery separation and no automatic posts or mention side effects.
2. Chrome DevTools checks use isolated state and a fake Codex process. They cover mixed-source search, unrelated working folders, opening an older reply, reminder creation/edit/cancel, a simulated failed submission preserving the draft, a live one-shot inbox event, and activity transitions through paused, waiting, ready and disconnected. Narrow layouts are inspected in a same-origin 390px iframe because the window manager does not honour requested browser dimensions.
3. The installed Codex MCP discovery smoke test runs against an isolated Codex home and confirms reminder/search tools are exposed and an actual saved user message is searchable without requesting an inference turn. Context-only empty sessions are discovered through the creating worker's retained catalogue, consistent with normal session listing. Production reminders are not created for testing, and production conversations are not used as browser fixtures.
