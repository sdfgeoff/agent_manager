# API-driven MCP discovery

1. src/board_api.rs registers the board's typed operations. The registration creates each concrete POST route and supplies its request/response validation, descriptions, read/write classification and human-only access policy. Schemars derives JSON Schema from those Rust types; the OpenAPI document is generated at runtime. There is no separately maintained OpenAPI JSON file or worker tool-name/schema table. Domain validation still enforces bounds, ownership and transactional business rules.
2. Authenticated GET /api/board/openapi.json returns OpenAPI 3.1 with self-contained JSON Schema 2020-12 input/output schemas. A human cookie receives the board's human-only operations too. Agent bearer credentials receive only agent-accessible operations; bearer requests with a browser Origin are rejected as before. Account administration, deployment and worker/session control are outside this board document. Auth checks precede ETag/304 handling.
3. Operations explicitly advertise MCP exposure through x-mcp metadata. The tool name comes from operationId; description, annotations and input schema come from the generated operation. API idempotency keys are kept internal to the bridge. The registry is also the source for read-only classification, so activity/search/reminder reads no longer emit board_changed events.
4. The worker's stdio bridge fetches the authenticated document at initialization and each tools/list, using ETags. Calling an unknown tool triggers a refresh too. Definitions are cached only in that MCP process and replaced after a complete valid document is parsed. Failed discovery returns an explicit error; rejected credentials invalidate the cache. There is no fallback to a stale hardcoded tool list or persistent plaintext catalogue.
5. Generic forwarding supports explicitly advertised, concrete JSON POST endpoints under /api/board/ on the configured origin. It ignores OpenAPI servers overrides and never resolves external references, follows redirects or forwards credentials to arbitrary destinations. Template/query/traversal paths and duplicate tool names are rejected. Unknown local adapter kinds are omitted instead of being treated as ordinary remote calls.
6. Two small local adapters remain: workspace-upload-v1 transforms a workspace path into the API's name/MIME/base64 fields; workspace-download-v1 turns attachment responses into MCP image/text content and optionally saves a private file without overwriting. Their alternate input views are derived from Rust types in the server registration. Canonical workspace checks remain in the worker. Local destination paths are not sent to the API.
7. To add a normal board feature, implement its domain behaviour and register its typed request/response with a description and access/read-only policy. Routing, OpenAPI and MCP discovery follow that registration; no worker upgrade is needed. New local filesystem behaviour or worker capabilities can still require worker code. Existing MCP clients may cache tools until they request tools/list or reconnect; the bridge does not force-refresh a running Codex turn. Normal idle agent resume rebuilds its MCP connection.
8. This is a one-time bridge upgrade: v0.6 workers need a server that offers discovery to use board MCP. Standalone sessions remain usable. Older workers keep their original tool list and can continue calling the existing board endpoints on newer servers. The server/worker envelope stays unversioned, with optional server-tools capability for diagnostics.

The generated document passed the official [OpenAPI 3.1 document schema](https://spec.openapis.org/oas/3.1/schema/2022-10-07), and its input/output schemas passed JSON Schema 2020-12 schema checks.

Verification covers real authenticated discovery and ETags, schema-driven endpoint validation, agent filtering, absence of read-triggered change events, an unchanged MCP process discovering a newly offered tool/argument, revoked credentials, unsafe endpoints and local adapter boundary/image/overwrite behaviour. The installed Codex smoke test discovers tools through an isolated real API server and uses no inference turn. UI compatibility is checked through Chrome DevTools with fixture data.
